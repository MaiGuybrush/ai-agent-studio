# ai-agent-studio v1 設計規格

本文件彙整 [Wayfinder 地圖](https://github.com/MaiGuybrush/ai-agent-studio/issues/1)上所有已定案的決定，供實作 session 直接使用。名詞定義以 repo 根目錄 [`CONTEXT.md`](../../CONTEXT.md) 為準；每節末尾的「來源」連到保存完整討論的票。

## 1. 範圍

**v1 涵蓋**：CIM Engineer 與 agent 進行 Interview，產出 Workflow Definition 與 Tool Spec → Naming Check → System Owner 做 Feasibility Review → 追蹤實作 → 全部 Tool Spec 已實作時，Requirement Ticket 自動變為「已完成」，再由 Business User 以「複製為 Markdown」交給 Cloud Agent Platform 的 skill 開發工具。

**v1 不做**
- MCP 工具本身的實作（走 CIM 既有開發流程，Studio 只追蹤狀態）。
- Cloud Agent Platform 的註冊自動化（由使用者手動註冊）。
- Skill Authoring（延到 phase 2，未必會做；參考方向見〈[Skill Authoring 套件結構與測試方式](https://github.com/MaiGuybrush/ai-agent-studio/issues/9)〉）。
- eCIM 串接：單號與需求描述都由人工輸入。
- 排程 agent 的描述（觸發條件、頻率）。
- 已實作工具的介面漂移監控。
- 系統知識庫（Knowledge Base／Knowledge Curator）。
- 配額、用量頁面、設定管理頁面、Feasibility Review 自動提醒。

## 2. 技術與架構

| 項目 | 決定 |
|---|---|
| 前端 | Angular（部門 template 專案，已實作 SSO） |
| 後端 | C#（部門 template 專案）；開發時以 `weekly-report-cowork/tools/mock-uac.mjs` 模擬 UAC |
| DB | PostgreSQL，**只有 C# 能存取** |
| Agent | Python 常駐 service，使用 **pydantic-ai**（不用 pydantic-deep：v1 不需要 workspace、execute、MCP 等功能） |
| 模型 | 只用公司核准的模型端點；端點與 key 放在 Python 設定檔 |
| 部署 | C# 與 Python 在同一台 **Windows** 主機；Python 用 uvicorn 加 Windows service 包裝（NSSM 或 `pywin32`，由實作選擇），只綁 `127.0.0.1` |
| repo | 單一 repo：`apps/web`（Angular）、`apps/api`（C#）、`apps/agent`（Python，含 agent 指令），一起發版部署 |
| instance | C# v1 只跑單一 instance（SSE 事件暫存在記憶體，這是已知上限） |

### 2.1 職責切分
- **C#**：SSO、權限、需求單、Tool Spec、Feasibility Review、通知、Naming Check、MCP 工具列舉（`ListToolsAsync()`）、PostgreSQL。**所有業務規則只寫在 C#。**
- **Python**：只負責執行 agent 與呼叫模型。不連 DB、不當 MCP client、不保存狀態（只保留執行中的 run）。
- **瀏覽器只連 C#**。C# 做完權限檢查後轉發 Python 的 SSE；`Last-Event-ID` 重連由 C# 處理（事件暫存在記憶體，run 結束即清除）。
- agent 的工具在 Python 端只是薄包裝，以 HTTP 轉給 C# 的內部 tool API。

### 2.2 Python service API
- `POST /runs`（回傳 SSE）：傳入 `run_id`、`messages`、最新草稿、人工修改 diff、run token、C# tool API base URL。最後一個事件帶本次新增的 messages 和 pydantic-ai 的 `usage()`。
- `POST /runs/{run_id}/cancel`
- `GET /health`

### 2.3 驗證
- C# → Python：固定 API key header，且 Python 只綁 `127.0.0.1`。
- Python → C#：每個 run 簽發短期 **run token**（Requirement Ticket id、CIM Engineer 帳號、到期時間）。tool API 只接受這個 token，而且只能操作該張需求單。

### 2.4 run 的執行規則
- 同一個 Interview 同時只能有一個 run；run 執行中不能送訊息，只能中止。
- 使用者訊息在 run 開始前寫入 DB；agent 新增的 messages 只在 run 正常結束時寫入。
- run 失敗或中止時，畫面顯示錯誤並提供重試；該回合的 agent 回覆捨棄，已寫入的草稿變更保留。
- C# 與 Python 之間的連線中斷時，Python 中止 run；C# 啟動時清除遺留的「執行中」標記。
- 草稿工具寫入 DB 後，C# 在該 run 的 SSE 串流中插入 `draft_changed` 事件。不另開 WebSocket 或第二條串流。
- 模型端點回 429 或配額錯誤時，Python 轉成明確的錯誤事件；前端顯示「模型額度不足或忙碌，請稍後再試」，該 run 標為錯誤。

來源：〈[C# 後端與 Python agent service 的切分與部署](https://github.com/MaiGuybrush/ai-agent-studio/issues/11)〉、〈[研究：pydantic-deep 作為常駐 service 的整合方式](https://github.com/MaiGuybrush/ai-agent-studio/issues/2)〉（其中 session 路徑、approvals、`deferred_tool_results`、POSIX 限制都已被取代）。

## 3. 身分與權限

### 3.1 身分來源
- UAC 的 JWT 只用來驗證身分（`empNo`）。
- 部門代碼：C# 帶使用者的 JWT 呼叫 `GET /HrEmployee/{empNo}?includeDept=true`（這個 API 只能查自己）。**不信任瀏覽器傳來的部門代碼。**
- 他人資料：用免認證的 `GET /HrEmployee/{empNo}/basic-info` 取得 `adId`，email 為 `{adId}@innolux.com`（網域放設定檔）。`basic-info` 只用來取得聯絡資料，**不能用於授權**。
- 不修改 UAC，也不申請高權限帳號。

### 3.2 CIM Engineer 的認定
- 設定檔列出 CIM 部門代碼清單，取部門代碼的前 N 碼比對（N 為設定值的字數，區分大小寫）。設定值含空字串時啟動失敗；清單為空時沒有人是 CIM Engineer。不做個人白名單。
- 每個 request 判斷一次；部門代碼在記憶體快取 10 分鐘。
- 查不到部門時不授予權限（fail closed）並顯示明確錯誤；快取過期後也不沿用舊值。唯讀權限不受影響。

### 3.3 權限表

| 對象 | 權限 |
|---|---|
| 負責的 CIM Engineer | 編輯、Interview、送出、取消、處理評估結果、標記實作狀態 |
| 任何 CIM Engineer | 建單；改派任何需求單（須附原因，寫入 `ticket_event`，**不寄通知**）；閱讀 Interview 對話紀錄 |
| Business User | 可以登入但不強制；唯讀，可用「複製為 Markdown」；不能留言 |
| System Owner | 評估、轉派、留言；也可以是同一張單的 CIM Engineer |
| 其他 SSO 使用者 | 需求單、Workflow Definition、Tool Spec、評估結果唯讀；看不到對話紀錄 |

- 負責人調離 CIM 部門後，該單對他變成唯讀，由其他 CIM Engineer 改派。
- 指定 Business User、System Owner、改派對象時都輸入工號，C# 用 `basic-info` 帶出資料；查無此人就擋下。改派 CIM Engineer 時無法驗證對方部門，等對方登入時才判斷。
- 需求單與 Tool Spec 保存工號加姓名快照。不建 `user_profile` 資料表。

來源：〈[權限與資料保存](https://github.com/MaiGuybrush/ai-agent-studio/issues/12)〉。

## 4. 系統設定

C# 的 JSON 設定檔，納入 git 版本控制，秘密值以 `${VAR}` 從環境變數帶入；改檔後自動重新載入。由 CIM 部門的 Studio 維護者修改，v1 不做管理頁面，變更歷史以 git 為準。

- **MCP Server List**：採 `mcpServers` 格式（同 Claude Code `.mcp.json`）。key 為 server id；`type` 只支援 `"http"`（`url`、`headers`）與 `"stdio"`（`command`、`args`、`env`），不支援 `sse`。
- **系統對照表**：系統 → System Owner 工號（只存工號）。
- **CIM 部門代碼清單**。
- 其他：Gitea 位址與服務帳號、email API、寄件信箱、email 網域、Studio 對外網址。

### 4.1 MCP 工具列舉
- 用官方 C# SDK **2.x**（`ModelContextProtocol.Core`）：`McpClient.CreateAsync` → `ListToolsAsync()`，取得 `Name`、`Description`、`InputSchema`、`OutputSchema`、`Annotations`。
- McpGateway 系的 server 只提供 Streamable HTTP（`/{dept}/mcp` 或 `/{dept}/{system}/mcp`），驗證用 `X-Api-Key`，輸出有 `outputSchema`。Gateway 使用 SDK 1.4.1，**實作時要先對 Gateway 做一次 smoke test**。
- 工具清單快取放記憶體，快取 key 要包含憑證身分；跨 server 的同名工具以 server key 當前綴區分。
- 工具命名慣例：`{department}_{system}_{action}[_v{major}]`。

來源：〈[研究：MCP Server List 設定格式與現有工具列舉](https://github.com/MaiGuybrush/ai-agent-studio/issues/3)〉。

## 5. 狀態機

### 5.1 Tool Spec 狀態
- **Reuse**：送出 Interview 時直接成為「已實作」，不需要 Feasibility Review。
- **Extend／New**：待評估 → 可行／不可行／附條件 → （附條件被接受後視同可行）→ 實作中 → 已實作。

### 5.2 Requirement Ticket Status
- 由人觸發的狀態只有「訪談中」與「已取消」，存在 DB。
- 其他狀態在查詢時由 Tool Spec 狀態推導：
  - 有任何 Tool Spec 處於待評估、不可行，或附條件但尚未接受 → **評估中**
  - 全部可行（含已接受條件），但還沒全部已實作 → **實作中**
  - 全部已實作 → **已完成**（只有 Reuse 的單，送出後會直接變成已完成）

### 5.3 轉換規則
1. CIM Engineer 建單時輸入需求單號（主鍵）、貼上需求描述，並綁定一位 Business User；之後可以改派負責人。
2. 負責的 CIM Engineer 送出 Interview 後，需求單進入評估中，並通知 System Owner。agent 不能自己送出。
3. **重開 Interview**：任何狀態都可以重開（包括已完成）。內容有改動或新增的 Tool Spec 重置為待評估；沒改動的保留原評估結果。
4. **不可行**：CIM Engineer 修改 Tool Spec 後送去重評，或刪除該 Tool Spec（Workflow Definition 一併調整）；全部不可行時走 Cancellation。
5. **附條件**：CIM Engineer 接受條件（條件記錄在 Tool Spec 上），或修改後重評。
6. CIM Engineer 手動把 Tool Spec 標為「實作中」。**不串 Gitea。**
7. 標為「已實作」之前必須通過 **Interface Compliance Check**（見 6.4）。
8. 全部 Tool Spec 已實作時，需求單自動變為已完成，並 email 通知 Business User 與 CIM Engineer。
9. **Cancellation**：只有負責的 CIM Engineer 能執行，須附原因；可以重開，重開後回到取消前的狀態。v1 沒有刪除功能。

來源：〈[需求單狀態機與流程規則](https://github.com/MaiGuybrush/ai-agent-studio/issues/4)〉（含移出 Skill Authoring 後的修訂）。

## 6. 文件格式

PostgreSQL JSONB 是正本。Markdown 只用在 System Owner 的評估畫面、email 摘要和「複製為 Markdown」；v1 不提供下載。

### 6.1 欄位型別
採 JSON Schema 子集：`string`／`number`／`integer`／`boolean`／`array`（含 `items`）／`object`（可巢狀），另外支援 `enum`、`format: date-time`、`required`、`description`。巢狀的子欄位也要跑 Naming Check。

### 6.2 Tool Spec
- **必填**：Kind（Reuse／Extend／New）、用途說明、對應系統、System Owner（Reuse 不需要）、input 欄位、output 欄位、所屬 Requirement Ticket、副作用旗標（唯讀／寫入）。
- **選填**：預期工具名稱、已接受的條件。
- Reuse／Extend：參照現有工具（MCP server key 加工具名稱），並保存當時的 schema 快照。
- Extend：只列出新增或修改的欄位。
- 一份 Tool Spec 只屬於一張 Requirement Ticket；其他需求單要用，等實作完成後以 Reuse 參照。
- 一份 Tool Spec 只對應一個系統、一位 System Owner；跨系統的工具在 Interview 時拆成多份。

### 6.3 Workflow Definition
線性步驟清單。每一步包含：說明、使用的 Tool Spec（或標為人工步驟）、輸入來源（使用者輸入，或前面某一步的某個 output 欄位）、輸出、是否需要人工核准。分支用條件文字描述。

### 6.4 Interface Compliance Check
CIM Engineer 提供 MCP server key 與工具名稱，C# 用 `ListToolsAsync()` 取得實際 schema 後比對：
- 工具必須存在。
- input：名稱、型別、`required` 都要相符，巢狀結構遞迴比對。
- output：名稱與型別相符即可。
- 實際工具多出必填 input → 擋下；多出的選填欄位和 output 只跑 Naming Check，命中別名時只警告。
- Extend 只比對 Tool Spec 有定義的欄位。
- `enum`：實際的值必須包含 Tool Spec 列出的全部值。
- Tool Spec 為 `number`、實際為 `integer` 算通過；反過來則不通過。
- 通過時把介面存進 `interface_snapshot`。

### 6.5 版本
- 每次送出 Interview，每份 Tool Spec 凍結成不可變的 **Tool Spec Revision**；Feasibility Review 綁定特定的 revision。
- 重開後只有內容有改動的 Tool Spec 會產生新 revision（**只改說明文字也算**）。System Owner 重評時可以看到與上一個 revision 的 diff。
- Workflow Definition 每次送出時凍結一份快照，和 Tool Spec 共用同一個 submission 編號；平常只保存最新的草稿。

### 6.6 複製為 Markdown
需求單頁面提供這個功能：內容是 Workflow Definition，加上每一步的 MCP server key 與工具名稱。Business User 把它貼到 Cloud Agent Platform 的 skill 開發工具。

來源：〈[Tool Spec 與 Workflow Definition 文件格式](https://github.com/MaiGuybrush/ai-agent-studio/issues/6)〉。

## 7. Naming Check 與 Tier1Vocabulary

### 7.1 取得詞彙
- 唯一正本是 McpGateway.Core 的 `src/McpGateway.Analyzers/Tier1Vocabulary.cs`，放在公司內部 Gitea，使用 **main 最新版**。Tier 2 `mcp-glossary.json` 已淘汰。
- C# 用 Gitea API 讀取原文，再用 `Microsoft.CodeAnalysis.CSharp` 做語法解析，抽出每個 `new GlossaryEntry(camel, Pascal, description, aliases[])`，並套用與 `Tier1VocabularyValidator` 相同的驗證規則。McpGateway.Core 不需要修改。
- 快取以 commit sha 為 key，TTL 5 分鐘，過期才比對 sha。解析、驗證或抓取失敗時沿用上一份好的版本，在 UI 上標示版本 sha 與時間，並通知 CIM Engineer；完全沒有快取時才擋下 Naming Check。

### 7.2 比對規則（依序）
1. 和標準名完全一致（依情境用 camel 或 Pascal）→ 通過。
2. 和標準名只差大小寫 → 建議改成標準寫法。
3. 命中別名（不分大小寫）→ 建議改成標準名。
4. 都沒有 → 新名詞，交給使用者確認。

### 7.3 在 Interview 中
- 每個欄位顯示狀態：通過／建議改名（可一鍵改成標準名）／新名詞。
- 只有 CIM Engineer 能確認新名詞，確認時要填說明；系統隨即用服務帳號在 McpGateway.Core 的 Gitea 開 issue（label `vocabulary-proposal`，附名詞、說明、可能的別名、來源需求單），該名詞成為 **Pending Term**。不開 PR。
- Pending Term 在 Naming Check 中視為已知；出現在 Tier1Vocabulary（標準名或別名）後自動移出清單。
- 每個欄位記錄 Naming Check 結果與詞彙 sha。
- **詞彙更新後重檢**：「已實作」之前的 Tool Spec 在開啟或送出時，如果詞彙 sha 落後就自動重跑。新命中只顯示警告，不會自動退回待評估。已實作的 Tool Spec 以 `interface_snapshot` 為準，不重檢。

來源：〈[Tier1Vocabulary 的同步方式](https://github.com/MaiGuybrush/ai-agent-studio/issues/5)〉、〈[Tool Spec 與 Workflow Definition 文件格式](https://github.com/MaiGuybrush/ai-agent-studio/issues/6)〉。

## 8. Interview

### 8.1 參與者
只有 CIM Engineer 與 agent 對話；Business User 的意見由 CIM Engineer 轉述。開場的脈絡來自建單時貼上的需求描述。

### 8.2 grill 流程（寫在 agent 指令中，可以回到前面的階段）
1. 任務目標與觸發時機
2. 逐步列出 Workflow Definition
3. 每一步對照 MCP Server List，判斷 Reuse／Extend／New
4. Extend／New 補上 input/output 欄位與副作用
5. Naming Check、建議 System Owner
6. 總結，並提示 CIM Engineer 可以送出

### 8.3 agent 工具（只開這些）
- 唯讀：`list_mcp_tools`、`naming_check(fields)`、`list_systems`、`get_requirement_ticket`、`search_tool_specs(keyword)`（查別張單進行中的 Tool Spec；相似時提醒 CIM Engineer，由他決定等待或另開 New）。
- 草稿：`upsert_workflow_step`、`upsert_tool_spec`、`delete_*`。
- **絕不呼叫業務 MCP 工具**，所以不需要核准流程。不開檔案系統與 execute。
- 沒有 `confirm_term` 工具：agent 只能標記新名詞並建議說明。

### 8.4 人工修改優先
- CIM Engineer 可以在對話中糾正，也可以直接編輯草稿（REST API，存檔時帶版本號）。
- agent 每一回合開始時讀取最新草稿，並收到人工修改的 diff。
- C# 記下人工修改過的欄位路徑；agent 寫入這些欄位時，tool API 拒絕並回傳目前的值。CIM Engineer 在對話中同意後，agent 帶 `override_human_edit=true` 才能寫入，並寫入 `ticket_event`。這些標記保留到該次 Interview 送出為止。

### 8.5 送出條件
- 每份 Extend／New Tool Spec 都已指定 System Owner。
- 沒有尚未確認的新名詞。
- 建議改名但沒有改的欄位都已填寫理由（理由記在該欄位上）。

### 8.6 對話保存與重開
- `Conversation` 存在 DB，可以跨天繼續。送出後停用輸入框。
- 重開 Interview 時開一段新對話，開場脈絡是上次送出的快照加上重開原因；舊對話保留供查閱。
- agent 指令放在 `apps/agent`，用 git 管理版本，隨部署更新；Studio 內不能編輯。

來源：〈[Interview agent 的行為與知識](https://github.com/MaiGuybrush/ai-agent-studio/issues/8)〉。

## 9. Feasibility Review

- **指派**：agent 依系統對照表建議 System Owner，CIM Engineer 確認。System Owner 可以轉派（須附原因），CIM Engineer 也可以改派；保留紀錄，並通知新的 System Owner。
- **回覆欄位**

  | 欄位 | 可行 | 附條件 | 不可行 |
  |---|---|---|---|
  | 結果 | 必填 | 必填 | 必填 |
  | 原因 | 選填 | 必填 | 必填 |
  | 條件內容 | — | 必填 | — |
  | 預估工時（人日） | 必填 | 必填 | 免填 |

- 在 CIM Engineer 處理之前（接受條件、修改或刪除），System Owner 可以修改回覆；每次修改都保留歷史。
- System Owner 不能修改 Tool Spec，只能在 Tool Spec 的留言串提問（不影響狀態）。正式的修改要求要用「附條件」或「不可行」加原因表達。留言串跨 revision 延續，每則留言標記所屬的 revision。
- **「待我評估」清單**：每一筆顯示 Tool Spec Revision、所屬 Workflow Definition（唯讀）、需求單號、CIM Engineer、Business User、**已等待 N 天**；不顯示 Interview 對話紀錄。
- 不做自動提醒，也不設逾期狀態；要催由 CIM Engineer 自己聯絡。

來源：〈[Feasibility Review 流程與通知](https://github.com/MaiGuybrush/ai-agent-studio/issues/7)〉、〈[通知與模型用量細節](https://github.com/MaiGuybrush/ai-agent-studio/issues/13)〉。

## 10. 通知（email）

### 10.1 事件（v1 只有這些）

| 事件 | 收件人 |
|---|---|
| 送評或重評 | System Owner |
| 轉派或改派 System Owner | 新的 System Owner |
| 回覆評估結果 | CIM Engineer |
| 有新留言 | 對方（CIM Engineer 或 System Owner） |
| 需求單已完成 | Business User、CIM Engineer |

改派需求單負責人時不寄通知。

### 10.2 寄送
- 採 outbox 模式：狀態變更和待寄 email 在同一個交易中寫入 `email_outbox`（只存收件人工號），由 C# `BackgroundService` 寄送。寄送時才用 `basic-info` 查出 email。
- 使用公司內部 email API，不走 SMTP。介面為 `IEmailSender`，有兩種實作：內部 API，以及開發用的寫入本機資料夾。
- 寄件人是專用服務信箱（例如 `ai-agent-studio@innolux.com`）；API 允許的話再設定顯示名稱。
- 重試採指數退避（1、5、15、60 分鐘…），最多 8 次。逾時、連線失敗、5xx、429 會重試；其他 4xx 和工號失效直接標為失敗。呼叫 API 前先記下嘗試次數，接受偶爾重複寄出。失敗只寫 log 和 `email_outbox` 的錯誤欄位；不追蹤退信。
- 內容：每個事件寄一封，繁體中文 HTML，寫明事件、需求單號、Tool Spec 名稱，並附一個直接連到 Studio 的連結。不附 Tool Spec 內容。範本寫在 C# 程式碼中，使用者不能取消訂閱。
- 已寄出的資料 90 天後清除。

來源：〈[通知與模型用量細節](https://github.com/MaiGuybrush/ai-agent-studio/issues/13)〉、〈[權限與資料保存](https://github.com/MaiGuybrush/ai-agent-studio/issues/12)〉。

## 11. 模型用量
C# 為每個 run 寫一筆 `agent_run`：需求單、CIM Engineer、起訖時間、結果（完成／取消／錯誤）、模型、input／output tokens、request 數。沒有收到最後一個事件時，用量記為未知，不另外補算。不做配額，也不做用量頁面，需要時由 Studio 維護者用 SQL 查詢。

## 12. 畫面

版面參考 [`prototype/interview-ui` 分支](https://github.com/MaiGuybrush/ai-agent-studio/tree/prototype/interview-ui) 的 `prototype/interview-ui.prototype.html`（丟棄式原型，實作時用 Angular 部門 template 重寫）。

- **Interview 頁採三欄版面**
  - 左：需求單資訊（單號、狀態、CIM Engineer、Business User）、需求描述、6 個階段的進度。
  - 中：對話區，佔最大寬度。
  - 右：分頁 Workflow Definition／Tool Spec／評估進度。Tool Spec 的每個欄位顯示 Naming Check 狀態與操作，並標示人工修改過的欄位；System Owner 選擇器標示 agent 的建議。
- 平常只顯示「送出前待處理 N 項」；完整的阻擋清單只在第 5、6 階段展開，送出按鈕在第 6 階段。
- 送出後停用輸入框，右側切換到評估進度；需求單已完成時出現「複製為 Markdown」。
- 其他畫面（需求單清單與建單、「待我評估」清單、評估畫面、唯讀的需求單頁）沒有原型，依本規格的欄位實作。

來源：〈[原型：訪談協作介面](https://github.com/MaiGuybrush/ai-agent-studio/issues/10)〉。

## 13. 資料表

全部由 C# 擁有；欄位細節留給實作決定。

| 資料表 | 內容 |
|---|---|
| `requirement_ticket` | 單號（主鍵）、需求描述、CIM Engineer、Business User（工號加姓名快照）、由人觸發的狀態、取消原因與取消前狀態 |
| `ticket_event` | 所有人工狀態變更（誰、何時、前後值）：取消、重開、改派、Tool Spec 手動狀態變更、`override_human_edit`；只能新增 |
| `interview` | 所屬單、重開原因、開場脈絡、`Conversation`（JSONB）、是否執行中 |
| `workflow_draft` | 每張單一份草稿（JSONB）、版本號、人工修改欄位標記 |
| `tool_spec` | 草稿（JSONB，含每個欄位的 Naming Check 結果與詞彙 sha）、版本號、人工修改欄位標記、Kind、System Owner（工號加姓名快照）、評估／實作狀態、目前的 revision |
| `submission` | 單號、submission 編號、Workflow Definition 快照 |
| `tool_spec_revision` | 不可變的 Tool Spec 內容，連到 `submission` |
| `feasibility_review` | 綁定 revision 的回覆；每次修改新增一筆 |
| `review_assignment` | System Owner 的轉派、改派紀錄與原因 |
| `tool_spec_comment` | 留言串，標記所屬的 revision |
| `pending_term` | 新名詞、說明、Gitea issue、確認者、狀態 |
| `interface_snapshot` | Interface Compliance Check 通過時的介面快照 |
| `email_outbox` | 收件人工號、內容、嘗試次數、錯誤、狀態 |
| `agent_run` | 見第 11 節 |

- Requirement Ticket Status 不存欄位（「訪談中」「已取消」除外）。
- 詞彙快取、工具清單快取、部門代碼快取都放在記憶體。
- **保存期限**：除了 `email_outbox` 已寄出的資料保留 90 天以外，全部永久保留。不做草稿的逐筆歷史，也不記錄讀取紀錄。

## 14. 仍待確認的事實

以下事實不影響設計，但實作到相關部分前要先確認：

**UAC／HR API**
- `GET /HrEmployee/{empNo}?includeDept=true` 和 `basic-info` 回應的欄位名稱；`basic-info` 是否包含姓名（沒有的話，姓名快照要另外處理）。
- 是否所有人的 `{adId}@innolux.com` 都有效（例如外包人員）。
- `tools/mock-uac.mjs` 要補上這兩個 endpoint，才能在本機開發。

**內部 email API**
- endpoint 與認證方式。
- 收件人格式是 email、`adId` 還是工號（如果直接接受工號，就不需要查 `basic-info` 和網域設定）。
- 寄件人能否自訂、內文是否支援 HTML、是否支援冪等鍵。
- 服務信箱是否需要申請。

**其他**
- 公司是否有資料保存政策；如果有，以政策為準。
- MCP C# SDK 2.x 對 McpGateway（SDK 1.4.1）的相容性：做一次 smoke test。
